# ADR-006: リリースブランチ経由の main 反映とスカッシュ運用

| :------------- | :-------------- |
| ステータス     | accepted        |

## 1. 背景・課題

- **背景**: `main` は本番相当の安定ブランチであり、リリースごとに 1 コミットで追える履歴が望ましい。一方、`develop` には観点ごとのコミットと PR 番号 `(#番号)` を残し、変更理由を追跡できる状態を保ちたい。
- **要求・制約**: `develop` の詳細な履歴を失わずに、`main` の履歴を簡潔に保つこと。
- **判断しない場合の影響**: `develop` から `main` へ直接スカッシュすると、`main` 側のスカッシュコミットと `develop` 側の元コミットが Git 上でつながらない。次回以降の PR で差分が重複表示され、競合も繰り返し発生する。

## 2. 決定

1. `main` への変更は、リリースブランチ（`release/<バージョン>`）経由に限る。`develop` から `main` への直接の PR は行わない。緊急の `hotfix/` だけを例外とする。
2. `release/` から `main` への PR は **Squash and merge** とする。`main` にはリリースごとに 1 コミットが積まれる。
3. 観点ごとのコミットと `(#番号)` は `develop` で管理する。
4. スカッシュ後に、`main` を `develop` へマージして戻す。この戻しマージは**必須**とし、**マージコミット（Create a merge commit）** で行う。スカッシュやリベースでは行わない。

## 3. 理由・代替案

### 採用理由

1. `main` の履歴をリリース単位の 1 コミットに保てる。
2. `develop` に詳細履歴が残るため、変更理由の追跡性を損なわない。
3. 戻しマージをマージコミットで行うと、スカッシュコミットが `develop` の祖先になり、履歴がつながる。以降の `release/` と `main` の差分が、新規の変更だけになる。
4. リリースブランチで凍結することで、リリース準備（バージョン更新、最終確認）と `develop` の継続開発を並行できる。

### 代替案

| 代替案                                     | 利点                   | 欠点・リスク                                                   | 採用しなかった理由                              |
| :----------------------------------------- | :--------------------- | :------------------------------------------------------------- | :---------------------------------------------- |
| `develop` → `main` を直接スカッシュ        | 手順が少ない           | 履歴がつながらず、差分の重複と競合が繰り返し発生する           | 継続運用で破綻するため                          |
| `develop` → `main` を通常のマージコミット  | 履歴がつながる         | `main` に `develop` の全コミットが入り、リリース単位で追えない | `main` を 1 コミット/リリースにする方針に反する |
| 戻しマージをスカッシュまたはリベースで行う | `develop` の履歴が直線 | 戻しがまた別コミットとなり、履歴がつながらない                 | 戻しの目的を達成できないため                    |

## 4. 影響・トレードオフ

- **利点**: `main` はリリース単位で読みやすい。`develop` は詳細履歴を保持する。
- **欠点・コスト**: リリースごとに、リリースブランチ作成と戻しマージの手順が増える。戻しマージを忘れると履歴が分岐する。
- **影響を受ける正本文書**: [Git Flow 運用規約](../setup/git_flow_and_branch_policy.md)、[リリース運用手順書](../how-to/release_branch_operation.md)
- **移行・ロールバック**: 既に履歴が分岐している場合は、初回の戻しマージで競合が出る可能性がある。手順書の「異常時の対応」に従う。
- **セキュリティ・運用上の影響**: GitHub のリポジトリ設定で、`main` へのマージ方式と `develop` へのマージ方式を分ける必要がある（手順書参照）。

## 6. 例外・見直し条件

- **例外・適用差異**: `hotfix/` は緊急時に限り `main` へ直接 PR を作成できる。マージ後は同様に `main` を `develop` へ戻す。
- **見直し条件**: 戻しマージの漏れが繰り返し発生した場合、またはリリース頻度が大きく変わった場合。
