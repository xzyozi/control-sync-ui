# ADR-008: サブモジュールとしての消費方式（ビルドの出力と参照の方法）

> 現在の仕様の正本は、決定後に、環境・開発基盤仕様書（CSU-ENV-001）と、統合の手順書（`docs/how-to/`）へ反映する。本書は判断理由の記録である。ステータスが `proposed` の間は、推奨案を、実装の暫定既定値として扱うが、確定ではない（確定時に `accepted` へ更新し、正規文書へ反映する。[ドキュメントガバナンス](../README.md) §5）。

## 1. 背景・課題

- **背景**: 本リポジトリは、Git サブモジュールとして、親プロジェクトの配下（例: `libs/<repo-name>`）に置かれる前提である（要件定義書 §1）。パッケージは、現在 `private: true` で、`dist/` は Git に入れていない。親がパッケージをどう参照して使うかが、決まっていない。
- **要求・制約**:
  - `core` は、外部ランタイムと UI フレームワークに依存しない（Zero-Dependency Core、要件定義書 §1。ポート分離は CN-02）。
  - 親プロジェクトのバンドラ（Vite、Webpack、esbuild）の違いで、壊れないこと（ENV §2。なお、#1 は Web Worker 隔離に伴う Worker 注入でのバンドラ差を扱う）。
  - 依存の固定とサプライチェーンの対策（`package-lock.json`、`npm ci`、公開から3日以内の版を避ける。ENV §4.6）。
  - 実装は TypeScript で、型定義（`.d.ts`）を、親に提供できること。
- **判断しない場合の影響**: `package.json` の `exports`、ビルドの出力先、統合の手順書、統合テスト（#20 の8〜10）が決められず、段階1の実装の形（ビルドの前提）も固まらない。

## 2. 決定

**推奨案（案 A）: 親がサブモジュール内で `npm ci` と `npm run build` を実行し、ビルドの出力（各パッケージの `dist/`）を、パッケージ名で参照する。**

1. サブモジュールのリポジトリは、**ソース（TypeScript）だけ**を、Git に入れる。`dist/` は、Git に入れない（`.gitignore` のとおり）。
2. 各パッケージの `package.json` は、ESM の `exports` と `types` を、`dist/` に向けて公開する。
3. 親は、次のいずれかの方法で、パッケージを参照する。
   - 親の npm ワークスペースに、サブモジュール内の `packages/*` を含める（例: ワークスペースの設定に `libs/<repo-name>/packages/*` を追加する）。
   - 親の `package.json` に、`file:` 依存（例: `"@csu/core": "file:libs/<repo-name>/packages/core"`）で、参照する。ただし、`packages/transport-http/package.json` 等がワークスペース外の環境で `"@csu/core": "*"` を持つと公開レジストリから解決を試みるおそれがあるため（ENV §4.6）、`file:` 依存を採る場合はワークスペース併用、`overrides`、またはローカル参照の整備を #20 の項目8 で確定する。
4. 親の CI とローカルの初期化の手順は、「サブモジュールの更新、`npm ci`（サブモジュール内）、`npm run build`」とし、統合の手順書に書く。

この決定は、バンドラの違いに依存せず、型定義も、`dist/` から、そのまま提供できる。

## 3. 理由・代替案

### 採用理由

1. ソースだけをコミットするので、ビルドの成果物と、ソースが食い違わない（1つの正本）。
2. ESM の `exports` と `types` を、パッケージごとに公開するだけなので、バンドラ固有の設定を必要としない。
3. `package-lock.json` を、サブモジュール側で固定できる（`npm ci`）。ENV §4.6 の方針と合う。

### 代替案

| 代替案                                                              | 利点                                                                 | 欠点・リスク                                                                                                  | 採用しなかった理由                                                                                         |
| :------------------------------------------------------------------ | :------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------ | :--------------------------------------------------------------------------------------------------------- |
| 案 B: ビルド済みの `dist/` を、リリース用のブランチ（タグ）に入れる | 親は、ビルドなしで、取り込める                                       | 成果物とソースが、食い違いうる。リリースの手順（ビルドのコミット）が、増える。サブモジュールの差分が、大きくなる | 現時点では、利用者が、自分の別プロジェクトや社内の限られた親に、限られている想定で、手間に見合わない。公開の段階（#20 の段階3）で再検討する |
| 案 C: 親が、ソース（TypeScript）を、直接ビルドに含める              | ビルドの手順が、親側に、1つ減る                                      | 親のバンドラと `tsconfig` に依存する（`strict`、`lib` の DOM なしなど、`core` の前提が、親に漏れる）。ENV §2（親のバンドラに依存しない）に反する                                                   | 親ごとに、設定の差が出て、`core` の前提（DOM に依存しない）を、機械的に守れない                           |
| 案 D: npm レジストリに公開する                                      | 一般的な配布方式で、バージョン管理が、容易                           | サブモジュールの前提（要件定義書 §1）と異なる。公開の手順と、認証情報の管理が、必要                           | 要件が、サブモジュールでの組み込みである。公開は、段階3で、必要になったときに、別の判断とする             |

## 4. 影響・トレードオフ

- **利点**: ソースが唯一の正本。バンドラに依存しない。
- **欠点・コスト**: 親が、サブモジュールの更新のたびに、`npm ci` と `npm run build` を、実行する必要がある。親の CI に、この手順を足す。
- **影響を受ける正本文書**: ENV（§4.3 のビルドと配布、§4.4 の QG-004）、統合の手順書（新規、#20 の9）、各パッケージの `package.json`（`exports`、`types`、`engines`。#20 の8）。
- **移行・ロールバック**: 実装前のため、移行は不要。案 B に切り替える場合は、`dist/` を入れる手順を、追加するだけで、案 A と両立できる。
- **セキュリティ・運用上の影響**: 親が、サブモジュールの `package-lock.json` に従って、`npm ci` を実行することで、依存の版が固定される（ENV §4.6）。なお、パッケージ間依存（例: `@csu/transport-http` の `@csu/core` 依存）が `file:` 参照時にレジストリへ解決されないよう、#20 の項目8 で参照方式を明示する。

## 6. 例外・見直し条件（必要な場合のみ）

- **例外・適用差異**: なし。
- **見直し条件**: 利用者が、社内の限られた親を、超えて広がる場合（公開）に、案 B または案 D を、再評価する。親のバンドラの制約で、案 A の参照が、できない場合も、再評価する。
- **見直し時期**: 段階3（#20 の13〜）の着手時、または、最初の親への組み込みの時。
