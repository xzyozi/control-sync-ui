# テスト計画・結果報告書
**状態同期基盤 v0.1 MVP：機能テスト要件に対するテストケースと結果**

> 本書は計画の段階で、実装がないため、すべてのケースの実績と判定は「未実施」である。実装の進行に合わせて、実績、判定、証跡を記録する。本書が要求・設計の正本を上書きしてはならない。問題が見つかった場合は、正本を更新する。

---

## 1. 目的・対象範囲

- **目的**: IF/API仕様書の機能テスト要件（TR-001〜013）と、DD の機能テスト要件（TR-101〜120）を、テストケースに対応付け、実装後に検証できる状態にする。
- **テスト対象**: サーバー（v0.1 の参照実装は `relay`）の IF-001〜IF-006、`core`（Domain Store、Control Store、Reactive Outbox、Sync Engine）、`storage-indexeddb`。
- **対象外**: 認証・認可（#8）、複数操作者の競合（#2）、Mailbox（#4）、OPFS（#5）、スナップショット（#6）、スキーマ進化（#7）、UI バインディング（#10）。性能・負荷テストは、v0.1 では実施しない。
- **関連する要求・設計**: [要件定義書](../features/CSU-REQ-001_最小要件定義書.md) の FR-01〜FR-05、NFR-01、NFR-03。[IF/API仕様書](../design/CSU-IF-001_IF仕様書.md) §6、[DD](../design/CSU-DD-001_詳細設計書.md) §5.1。

## 2. テスト戦略・合格基準

- [x] TDD（`core` の純粋なロジック、`relay` の判定ロジック）
- [x] 結合テスト（`core` と `relay` を、Node の中で通信させる）
- [x] 手動確認（ブラウザでの IndexedDB、EventSource の動作、`demo` の2画面）
- [ ] characterization test、E2E、性能・負荷、セキュリティ、移行・復旧
- **選択理由**: `core` はブラウザ API に依存しないため、Node で速く検証できる。IF の契約は、`core` と `relay` の結合で、メッセージの形式と順序を確かめる。IndexedDB と EventSource は、ブラウザ固有の挙動を持つため、手動確認で補う。
- **合格基準**: 対象とするすべてのケースが Pass で、未実施のケースは §6 に理由と代替確認を記録している。
- **適用する品質ゲート**: [環境・開発基盤仕様書](../setup/CSU-ENV-001_環境・開発基盤仕様書.md) の QG-001〜QG-004、QG-007（実行コマンドと合格基準は再掲しない）。
- **使用する証跡**: CI の実行結果（QG-003）、手動確認の記録（ブラウザの種類と版、操作、結果）。

## 3. テスト環境・前提条件

- **環境**: [環境・開発基盤仕様書](../setup/CSU-ENV-001_環境・開発基盤仕様書.md) §3 のローカル開発と CI（Node.js 20.x 以上）。手動確認は、IndexedDB と EventSource を使えるブラウザ（版は実装時に決める）。
- **テストデータ**: テスト用の `roomId`、`targetId`、`operatorId`、イベント（`payload.type` を持つ JSON）。秘密情報や個人情報を含めない。
- **前提条件**: 結合テストでは、`relay` を、テストごとに新しい状態で起動する。TTL と間隔は、テストでは短い値に差し替えられること（既定値は DD §1.3）。
- **実行方法**: 実装後に、環境・開発基盤仕様書の QG-003 のコマンドと CI で実行する。手動確認は、実装後に手順を追記する。
