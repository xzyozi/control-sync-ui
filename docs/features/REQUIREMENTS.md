# 最小要件定義書（v0.1 MVP）

## 1. 目的とスコープ

- **目的:** ブラウザ側に状態の正本と決定論的な計算ロジックを持たせ、外部PCの画面操作（制御状態）に応じてデータ送信を動的に制御できる、UI非依存のTypeScript同期基盤の最小核を構築する。
- **提供形態:** Gitサブモジュールとして親プロジェクトへ組み込み可能な構成とする。コアパッケージは外部ランタイムおよびUIフレームワークに依存しない（Zero-Dependency Core）。
- **管理先:** 後続課題は GitHub Issues で管理する。本文書は、Issue から参照できる最初の要求の正本として `docs/features/` に置く。Issue の議論履歴とは分け、確定した内容だけを記載する。

## 2. 制約（設計方針として固定する事項）

次の事項は、v0.1 の要求を満たすために固定する制約である。詳細な構造と契約は、基本設計書（BD）とIF/API仕様書ができた時点で、そちらを正本とする。

| ID    | 制約                                                                                                                                                                                  |
| :---- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| CN-01 | `core`（純粋TS基盤）、`relay`（単体検証用の最小外部サーバー）、`demo`（2画面動作確認用）をディレクトリ単位で物理分離する。                                                            |
| CN-02 | 永続化（`StoragePort`）と通信（`TransportPort`）をインターフェースで分離し、コアからブラウザAPIや通信プロトコルの実装詳細を隠蔽する。                                                 |
| CN-03 | コアはDOMに依存しない。v0.1ではメインスレッド動作を標準とし、Web Worker隔離は後続課題（[#1](https://github.com/xzyozi/control-sync-ui/issues/1)）とする。                             |
| CN-04 | 状態遷移は純粋関数（Reducer）と追記型イベントログで管理する。                                                                                                                         |
| CN-05 | 競合制御の初期仕様は、TTLとハートビートによる単一排他ロック（Exclusive Lease Lock）に固定する。差し替えは後続課題（[#2](https://github.com/xzyozi/control-sync-ui/issues/2)）とする。 |

## 3. 機能要件と受け入れ条件

### FR-01 決定論的ドメインストア（Domain Store）

- JSONシリアライズ可能な構造化ドキュメントを対象とし、状態遷移をReducerと追記型イベントログで管理する。
- 初期ストレージアダプターとして **IndexedDB** を提供する。

**受け入れ条件**

- 同じ初期状態と同じイベント列を適用すると、実行回数や実行環境によらず同じ状態になる。
- ストアを閉じて開き直した後、イベントログから同じ状態を復元できる。

### FR-02 制御ストア（Control Store）と排他ロック

- 外部PCの画面操作に由来する制御状態（送信対象フィルタ、現在の操作権限者）を、ドメイン状態と分離して管理する。
- 制御状態の変更ごとに、単調増加する `controlSeq` を発行する。
- 排他ロックはTTLとハートビートで管理する。

**受け入れ条件**

- 制御状態を変更しても、ドメイン状態は変化しない。
- 制御状態を変更するたびに `controlSeq` が増加し、減少や重複が起きない。
- ロック保持者以外からの制御状態の変更は拒否される。
- ハートビートが途絶えてTTLが経過すると、ロックが解放され、別の操作者が取得できる。

### FR-03 動的送信エンジン（Reactive Outbox）

- ローカルの未送信イベントと `Control Store` の最新状態を突き合わせ、条件に合致するデータだけを外部へ送信する。
- 送信パケットには、適用時点の `controlSeq` を付与する。

**受け入れ条件**

- 送信対象フィルタに合致しないイベントは送信されない。
- 送信パケットに `controlSeq` が含まれる。
- サーバーの現在の `controlSeq` より古い値の送信パケットは、サーバーが拒否する。
- 制御状態が変わると、未送信イベントへ新しいフィルタが適用される。

### FR-04 Control-First Sync（最小同期プロトコル）

- 接続・再接続時は、先に `Control Store` の最新状態をサーバーからPullして確定させる。その後に `Reactive Outbox` の評価とPushを行う。
- `relay` は、Room単位の分離、`controlSeq` の検証、イベントの順序付け、更新通知だけを行う薄いリレーとする。

**受け入れ条件**

- 再接続時、制御状態のPullが完了する前にはPushが行われない。
- 異なるRoomのイベントと制御状態は、互いに参照も変更もできない。
- `relay` は、受け付けたイベントに一意で増加する順序を付ける。
- 制御状態またはイベントが更新されると、接続中のクライアントへ通知される。

### FR-05 オフライン時のコマンド挙動（Fail-Fast）

- 外部PCからの操作・要求時に対象端末がオフラインの場合、サーバーは即座に `TARGET_OFFLINE` エラーを返す。

**受け入れ条件**

- 対象端末がオフラインのとき、操作要求に対して `TARGET_OFFLINE` が返り、要求は滞留しない。
- 対象端末がオンラインのときは、同じ要求が受け付けられる。

## 4. 非機能・制約要件

### NFR-01 型安全性

TypeScript `strict: true` を満たす。境界でやり取りするイベントと制御メッセージの型契約を明確に定義する。

**受け入れ条件:** `strict: true` で型検査がエラーなしで通る。

### NFR-02 Web単体制約

ブラウザタブを閉じている間のバックグラウンド処理と常駐応答は、スコープ外とする（[#4](https://github.com/xzyozi/control-sync-ui/issues/4) で扱う）。

### NFR-03 スキーマバージョン検出

イベントと制御メッセージに、`schemaVersion` を必須で付与する。不一致を検出した場合は「安全にエラー停止」する。ここでの「安全にエラー停止」は、次の3つを満たすことと定義する。

- 不一致のメッセージを適用しない。
- 永続状態を変更しない。
- エラーを呼び出し元へ通知する。

**受け入れ条件**

- `schemaVersion` が欠けたメッセージは、型検査または受信時の検証で拒否される。
- `schemaVersion` が一致しないメッセージを受信しても、状態は変化せず、エラーが通知される。

次の事項は、要求として確定していない。決定した時点で、本文または BD/IF/API仕様書へ反映する。

| ID    | 未決事項                                                                                                        | 提案                                                                        |
| :---- | :-------------------------------------------------------------------------------------------------------------- | :-------------------------------------------------------------------------- |
| OP-01 | `controlSeq` の発行元（クライアントかサーバーか）                                                               | `relay` が発行する。順序付けの責務と同じ場所に置けるため。                  |
| OP-02 | 「オフライン」の判定方法                                                                                        | 更新通知の接続の有無と、ハートビートのTTL切れで判定する。                   |
| OP-03 | 更新通知の方式（SSE以外を使うか）                                                                               | v0.1 はSSEを標準とし、`TransportPort` の裏側で差し替え可能にする。          |
| OP-04 | IndexedDBアダプターの置き場所。Zero-Dependency Core の `core` に、ブラウザAPIに依存するアダプターを含めてよいか | `core` はポートのインターフェースだけとし、アダプターは別パッケージにする。 |
