# リリース運用手順書

**リリースブランチ経由の main 反映と、main から develop への戻しマージ**

---

## 1. 目的・対象範囲

- **目的**: `main` をリリースごとに 1 コミットで更新し、`develop` と `main` の履歴をつなげた状態を保つ。
- **対象**: `release/` ブランチの作成、`main` への Squash and merge、`main` から `develop` への戻しマージ。
- **対象外**: 通常の `feat/`、`fix/`、`docs/` ブランチの運用（[Git Flow 運用規約](../setup/git_flow_and_branch_policy.md)を参照）。
- **実施タイミング**: リリース時。緊急の `hotfix/` 反映時（手順 B）。

### 運用ルール（ADR-006）

| ルール                                              | 内容                                                                              |
| :-------------------------------------------------- | :-------------------------------------------------------------------------------- |
| `main` への変更はリリースブランチ経由に限る         | `develop` → `main` の直接 PR は行わない。緊急の `hotfix/` だけが例外。            |
| `release/` → `main` は Squash and merge             | `main` にはリリースごとに 1 コミットが積まれる。                                  |
| 履歴は `develop` で管理する                         | 観点ごとのコミットと `(#番号)` は `develop` に残る。                              |
| スカッシュ後に `main` を `develop` へマージして戻す | **必須**。**マージコミット**で入れる。スカッシュにすると、再び履歴がつながらない。 |

## 2. 前提条件・注意事項

- **実行者・必要権限**: `main` と `develop` へのマージ権限を持つ担当者。
- **事前確認**:
  - リポジトリ設定で、`main` と `develop` のマージ方式を使い分けられること。`release/` → `main` では Squash and merge、`main` → `develop` では Create a merge commit を選択できる状態にする。
  - `develop` が CI 成功状態であること。
- **停止・中断条件**: CI が失敗している場合、またはリリース対象外の変更が `release/` に含まれている場合。
- **安全上の注意**: 戻しマージで Squash and merge または Rebase and merge を選ばない。force push はしない。

## 3. 手順

### 手順 A: 通常リリース

| No. | 操作・確認内容                                                                                                   | 期待結果                                                  | 異常時の対応                                                                 |
| :-- | :--------------------------------------------------------------------------------------------------------------- | :-------------------------------------------------------- | :--------------------------------------------------------------------------- |
| A-1 | `develop` を最新化し、`git switch -c release/<バージョン>` でリリースブランチを作成して push する                | `release/<バージョン>` がリモートに存在する               | 作成元が `develop` の最新か確認する。                                        |
| A-2 | リリース準備（バージョン更新など）が必要な場合は、`release/` 上でコミットする                                    | 変更が `release/` に反映され、CI が成功する               | CI 失敗時は原因を修正してから進む。                                          |
| A-3 | `release/<バージョン>` → `main` の PR を作成する。`develop` → `main` の PR は作らない                            | base が `main`、compare が `release/<バージョン>` の PR   | base または compare を誤った場合は PR を閉じて作り直す。                     |
| A-4 | PR を **Squash and merge** でマージする。コミットメッセージは `[種別] 概要` 形式で、リリース内容を要約する      | `main` に 1 コミットが追加される                          | 別方式でマージした場合は、手順の続行前に担当者へ報告する。                   |
| A-5 | `main` → `develop` の PR を作成し、**Create a merge commit** でマージする（**必須**）                            | `develop` に `main` のスカッシュコミットが祖先として入る  | 競合時は「補足・例外」の EX-001 を参照する。スカッシュでは絶対にマージしない。 |
| A-6 | 戻しマージ後に確認する。`git fetch` 後、`git log --oneline origin/develop..origin/main` を実行する               | 出力が空（`main` に `develop` 未反映のコミットがない）    | 出力がある場合は A-5 が未完了。再度 `main` → `develop` を実施する。          |
| A-7 | `release/<バージョン>` を削除する（自動削除設定が有効なら不要）                                                  | リモートの `release/` ブランチが残っていない             | 手動で削除する。                                                             |

### 手順 B: 緊急 hotfix（例外）

| No. | 操作・確認内容                                                                              | 期待結果                              | 異常時の対応                                               |
| :-- | :------------------------------------------------------------------------------------------ | :------------------------------------ | :--------------------------------------------------------- |
| B-1 | `main` から `git switch -c hotfix/<修正内容>` で分岐し、修正をコミットして push する       | `hotfix/<修正内容>` がリモートに存在  | 分岐元が `main` か確認する。                               |
| B-2 | `hotfix/<修正内容>` → `main` の PR を作成し、**Squash and merge** でマージする             | `main` に 1 コミットが追加される      | CI 失敗時は修正してから再度マージする。                    |
| B-3 | 手順 A-5 と同じく、`main` → `develop` を **Create a merge commit** で戻す（**必須**）      | `develop` に修正が反映され履歴がつながる | 競合時は EX-001 を参照する。                               |
| B-4 | 手順 A-6 で確認する                                                                         | 出力が空                              | A-5 と同様に再実施する。                                   |

## 4. 補足・例外

| ID     | 対象手順 | 標準との差異                         | 理由・制約                                         | 影響                         | 代替対応                                                                                       | 解除条件           |
| :----- | :------- | :----------------------------------- | :------------------------------------------------- | :--------------------------- | :--------------------------------------------------------------------------------------------- | :----------------- |
| EX-001 | A-5, B-3 | 戻しマージで競合が発生する           | `develop` に `release/` 以降の変更が先行している   | 戻しマージ PR がマージできない | `develop` から作業ブランチを作成し `main` をマージして競合を解消後、`develop` へ **マージコミット** で PR する | 競合解消後の PR 完了 |
