# IF/API仕様書（外部インターフェース契約）
**対象端末・外部PC・サーバーのあいだの HTTP（Pull、Push、lease、presence）と SSE（更新通知）**

---

## 1. 概要とSSOT境界

### 1.1 対象インターフェースの目的

- **提供者 / 利用者**: 提供者はサーバー（v0.1 の参照実装は `relay`）。利用者は対象端末（ブラウザ）と外部PC（操作者）。
- **連携の目的**: 外部PCの操作に由来する制御状態を対象端末へ伝え、対象端末が制御状態に応じてイベントを送信するため。
- **対象範囲**: 制御状態の取得、イベントの送信、制御状態の変更、lease の取得・更新・解放、presence heartbeat、更新通知。
- **対象外**: 認証・認可（[#8](https://github.com/xzyozi/control-sync-ui/issues/8)）、タブ閉鎖中の要求の滞留（[#4](https://github.com/xzyozi/control-sync-ui/issues/4)）、複数操作者の競合ポリシー（[#2](https://github.com/xzyozi/control-sync-ui/issues/2)）。

### 1.2 単一責任範囲 (SSOT) と文書境界

- **本書の正本範囲**: `external_interface`。システム境界を越えるメッセージ、エンドポイント、エラーコード、互換性の正本とする。
- **BDとの関係**: 境界の位置、ロックとオフラインの判定をサーバーが行う方針、制御状態を Room 単位で持つ方針（D-01、D-02、D-04、D-06）は [基本設計書](./CSU-BD-001_基本設計書.md) を正本とする。本書はそれを接続契約へ具体化する。
- **DDとの関係**: 内部の DTO、制御フロー、状態遷移、TTL の具体値、lease の期限の検出方法は [DD](./CSU-DD-001_詳細設計書.md) を正本とする。機能IDとの対応は、2.1 の表に示す。
- **DSとの関係**: 保存後の形式は [DS](./CSU-DS-001_データ構造仕様書.md) を正本とする。本書は受信形式だけを定義する。
- **要件定義書との関係**: FR-04 の「Pull と Push は HTTP、更新通知は SSE」の記述は、本書を正本とする。要件定義書側は、後続の改訂で参照だけにする（#11）。
- **責務の対象外**: TTL と再試行の具体値、サーバー内部の順序付けの実装。
- **矛盾時の扱い**: 文書の更新日ではなく、該当する `ssot_scope` の正本を更新し、関連文書を追従させる。

## 2. インターフェース共通仕様

### 2.1 インターフェース一覧

| IF-ID  | インターフェース名       | 方向                | 方式                 | エンドポイント                  | 対応するDD機能ID           | 状態 |
| :----- | :----------------------- | :------------------ | :------------------- | :------------------------------ | :------------------------- | :--- |
| IF-001 | 制御状態の取得（Pull）   | 対象端末 → サーバー | HTTP `GET`           | `/rooms/{roomId}/control`       | F-002、F-004、F-008        | 計画 |
| IF-002 | イベントの送信（Push）   | 対象端末 → サーバー | HTTP `POST`          | `/rooms/{roomId}/events`        | F-003、F-004、F-005、F-008 | 計画 |
| IF-003 | 更新通知                 | サーバー → 対象端末 | SSE（`GET`、片方向） | `/rooms/{roomId}/notifications` | F-004、F-005、F-008        | 計画 |
| IF-004 | presence heartbeat       | 対象端末 → サーバー | HTTP `POST`          | `/rooms/{roomId}/presence`      | F-004、F-007、F-008        | 計画 |
| IF-005 | lease の取得・更新・解放 | 外部PC → サーバー   | HTTP `POST`          | `/rooms/{roomId}/lease`         | F-005、F-006、F-008        | 計画 |
| IF-006 | 送信対象フィルタの変更   | 外部PC → サーバー   | HTTP `POST`          | `/rooms/{roomId}/control`       | F-005、F-006、F-007、F-008 | 計画 |

IF-005 の更新が lease heartbeat に当たる。IF-004（presence heartbeat）とは、送り手も意味も異なる別のインターフェースである（BD D-02）。`{roomId}` はパスパラメータで、以降の表では「パス」と示す。

### 2.2 共通ルール

- **プロトコル・トランスポート**: HTTP と SSE。通信の保護方式（TLS など）は、v0.1 の単体検証では対象外とし、#8 で定める。
- **データ形式・文字コード**: リクエストとレスポンスの本文は JSON、UTF-8。SSE の通知の `data` も JSON とする。
- **時刻・タイムゾーン**: メッセージに時刻を含める場合は、UTC の ISO 8601 形式とする。lease と presence の期限の判定は、サーバーの時刻だけで行う。
- **識別子・相関ID**: Room を `roomId`（パス）、対象端末を `targetId`、外部PCの操作者を `operatorId` で識別する。リクエストごとに `requestId` を付け、応答とログで同じ値を使う。
- **共通項目の載せ場所**: `schemaVersion` と `requestId` は、リクエスト本文ではなく、次の場所に載せる。SSE（EventSource）は独自ヘッダーを送れないため、IF-003 だけはクエリパラメータとする。

| 項目            | HTTP のリクエスト（IF-001、002、004、005、006） | SSE の接続（IF-003）             | 応答・通知                                              |
| :-------------- | :---------------------------------------------- | :------------------------------- | :------------------------------------------------------ |
| `schemaVersion` | ヘッダー `X-Schema-Version`（必須）             | クエリパラメータ `schemaVersion` | 通知の `data` に `schemaVersion` を含める。             |
| `requestId`     | ヘッダー `X-Request-Id`（必須）                 | クエリパラメータ `requestId`     | HTTP の応答は、ヘッダー `X-Request-Id` に同じ値を返す。 |

- **欠落時の扱い**: `schemaVersion` または `requestId` が欠落している場合は、`INVALID_MESSAGE` で拒否する。値が一致しない場合は、`SCHEMA_VERSION_MISMATCH` で拒否する。
- **エラー応答の共通形式**: エラーのときは、HTTP ステータスと、次の項目を持つ JSON を返す。

| フィールド   | データ型 | 必須性 | NULL可 | 意味                                                     |
| :----------- | :------- | :----: | :----: | :------------------------------------------------------- |
| `code`       | 文字列   |  必須  |  不可  | エラーコード。                                           |
| `message`    | 文字列   |  必須  |  不可  | 人が読む説明。機械的な処理に使ってはならない。           |
| `requestId`  | 文字列   |  必須  |  不可  | リクエストの `X-Request-Id` と同じ値。                   |
| `controlSeq` | 整数     |  任意  |  不可  | `STALE_CONTROL_SEQ` のときだけ、サーバーの最新値を返す。 |

- **HTTP ステータスの割り当て**:

| エラーコード              | HTTP ステータス |
| :------------------------ | :-------------- |
| `INVALID_MESSAGE`         | 400             |
| `SCHEMA_VERSION_MISMATCH` | 400             |
| `LOCK_NOT_HELD`           | 403             |
| `ROOM_NOT_FOUND`          | 404             |
| `STALE_CONTROL_SEQ`       | 409             |
| `LOCK_HELD_BY_OTHER`      | 409             |
| `TARGET_OFFLINE`          | 409             |

- **成功時の HTTP ステータス**: 本文を返す場合は 200、本文を返さない場合（IF-004）は 204、IF-003 の接続の確立は 200（`text/event-stream`）とする。
- **タイムアウト・再試行**: 具体値は DD で定める。再試行してよいかは、各 IF の冪等性と、エラー応答の再試行可否の列に従う。
- **利用制限**: v0.1 では定めない。

## 4. インターフェース別契約

共通項目（`schemaVersion`、`requestId`）は、2.2 のとおり本文以外に載せる。以降の表では、IF固有の項目だけを示す。形式の例は示さず、フィールドを表で定義する。

各エラー応答の表の「再試行可否」は、呼び出し側が、条件の解消後に再実行してよいかを表す（「条件付き」は、その条件が解消した後に限り再実行してよい）。クライアントが自動で再試行する回数は、DD の §4.1 を正本とする。

### 4.1 契約（IF-ID: IF-001 制御状態の取得）

- **概要**: 対象端末が、Room の最新の制御状態と `controlSeq` を取得する。接続・再接続時に、Push より先に必ず実行する（Control-First Sync）。制御状態は Room で1つ持つ（BD D-06）。
- **呼び出し方式**: `GET /rooms/{roomId}/control`。
- **冪等性**: あり。再送してよい。
- **事前条件 / 事後条件**: 事前条件は `roomId` が存在すること。事後条件は、応答の `controlSeq` が、サーバーが発行した最新の値であること。

#### 4.1.1 リクエスト

| フィールド | 載せ場所         | データ型 | 必須性 | NULL可 | バリデーション・制約                                                                      |
| :--------- | :--------------- | :------- | :----: | :----: | :---------------------------------------------------------------------------------------- |
| `roomId`   | パス             | 文字列   |  必須  |  不可  | 空でない。                                                                                |
| `targetId` | クエリパラメータ | 文字列   |  必須  |  不可  | 空でない。Room 内で一意。呼び出した端末を識別するために使い、取得する制御状態は選ばない。 |

#### 4.1.2 レスポンス

| フィールド   | データ型     | 必須性 | NULL可 | 意味・取り得る値                                                                                       |
| :----------- | :----------- | :----: | :----: | :----------------------------------------------------------------------------------------------------- |
| `controlSeq` | 整数         |  必須  |  不可  | サーバーが発行した最新の値。0 以上。                                                                   |
| `control`    | オブジェクト |  必須  |  不可  | 制御状態。`sendFilter`（送信対象フィルタ）と `holderId`（現在の操作権限者。なしの場合は NULL）を持つ。 |

#### 4.1.3 エラー応答

| エラーコード              | 発生条件                                | 応答形式            | 呼び出し側の対応                             | 再試行可否 |
| :------------------------ | :-------------------------------------- | :------------------ | :------------------------------------------- | :--------- |
| `INVALID_MESSAGE`         | 共通項目の欠落、`targetId` の欠落など。 | 400、共通エラー形式 | 送信内容を修正する。                         | 不可       |
| `SCHEMA_VERSION_MISMATCH` | `schemaVersion` が一致しない。          | 400、共通エラー形式 | 状態を変えずに停止し、呼び出し元へ通知する。 | 不可       |
| `ROOM_NOT_FOUND`          | `roomId` が存在しない。                 | 404、共通エラー形式 | `roomId` を確認する。                        | 不可       |

### 4.2 契約（IF-ID: IF-002 イベントの送信）

- **概要**: 対象端末が、Reactive Outbox で選ばれたイベントをサーバーへ送る。
- **呼び出し方式**: `POST /rooms/{roomId}/events`。
- **冪等性**: 条件付き。同じ `eventId` の再送は、二重に追加されない。
- **事前条件 / 事後条件**: 事前条件は、同じ接続での IF-001 が完了していること。事後条件は、受理されたイベントにサーバーが順序番号 `eventSeq` を付けていること。同じ Room の中では、`eventSeq` は一意で増加する。Room をまたいだ関係は保証しない（[DD](./CSU-DD-001_詳細設計書.md) V-10）。

#### 4.2.1 リクエスト

| フィールド   | 載せ場所 | データ型 | 必須性 | NULL可 | バリデーション・制約                                                                                                                                        |
| :----------- | :------- | :------- | :----: | :----: | :---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `roomId`     | パス     | 文字列   |  必須  |  不可  | 空でない。                                                                                                                                                  |
| `targetId`   | 本文     | 文字列   |  必須  |  不可  | 空でない。                                                                                                                                                  |
| `controlSeq` | 本文     | 整数     |  必須  |  不可  | Outbox が送信の評価に使った値。**サーバーの最新値と一致すること。** 最新値より小さい場合は `STALE_CONTROL_SEQ`、大きい場合は `INVALID_MESSAGE` で拒否する。 |
| `events`     | 本文     | 配列     |  必須  |  不可  | 1件以上。各要素は `eventId`（文字列、一意）と `payload`（JSON）を持つ。                                                                                     |

#### 4.2.2 レスポンス

| フィールド | データ型 | 必須性 | NULL可 | 意味・取り得る値                                            |
| :--------- | :------- | :----: | :----: | :---------------------------------------------------------- |
| `accepted` | 配列     |  必須  |  不可  | 受理したイベントの `eventId` と、付与した `eventSeq` の組。 |

#### 4.2.3 エラー応答

| エラーコード              | 発生条件                                                                                 | 応答形式            | 呼び出し側の対応                                                                                                                                                                    | 再試行可否 |
| :------------------------ | :--------------------------------------------------------------------------------------- | :------------------ | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | :--------- |
| `STALE_CONTROL_SEQ`       | 送信の `controlSeq` が、サーバーの最新値より小さい。応答に最新の `controlSeq` を含める。 | 409、共通エラー形式 | IF-001 で制御状態を取得し直す。拒否されたイベントは破棄せず、取得し直した制御状態で再評価する（[DD §3.2](./CSU-DD-001_詳細設計書.md)）。連続の再評価の上限は、DD の V-11 で定める。 | 条件付き   |
| `SCHEMA_VERSION_MISMATCH` | `schemaVersion` が一致しない。                                                           | 400、共通エラー形式 | 状態を変えずに停止し、呼び出し元へ通知する。                                                                                                                                        | 不可       |
| `ROOM_NOT_FOUND`          | `roomId` が存在しない。                                                                  | 404、共通エラー形式 | `roomId` を確認する。                                                                                                                                                               | 不可       |
| `INVALID_MESSAGE`         | 必須項目の欠落、型の誤り、サーバーが発行していない大きい `controlSeq` など。             | 400、共通エラー形式 | 送信内容を修正する。                                                                                                                                                                | 不可       |

### 4.3 契約（IF-ID: IF-003 更新通知）

- **概要**: サーバーが、制御状態またはイベントが更新されたことを、接続中の対象端末へ通知する。サーバーから対象端末への片方向である。
- **呼び出し方式**: `GET /rooms/{roomId}/notifications`。対象端末が Room 単位で接続を確立し、サーバーが SSE のストリームで通知を流す。
- **冪等性**: 該当しない（購読）。
- **事前条件 / 事後条件**: 事前条件は `roomId` が存在すること。この接続の有無が、オフライン判定の条件の1つになる（BD D-04）。接続が開いた（`open`）ときは、初回でも、ブラウザの自動再接続のときでも、毎回 IF-001 で最新の制御状態を取得してから、IF-002 を実行する（Control-First Sync）。自動再接続はブラウザの中で行われるので、クライアントは `open` のたびに IF-001 を実行する処理を持つ。
- **`requestId` の扱い**: IF-003 の `requestId` は、接続単位とする。ブラウザの自動再接続は、同じ URL（同じ `requestId`）で行われるため、再利用してよい。2.2 の「リクエストごとに付ける」の例外とする。

#### 4.3.1 リクエスト（接続）

| フィールド      | 載せ場所         | データ型 | 必須性 | NULL可 | バリデーション・制約 |
| :-------------- | :--------------- | :------- | :----: | :----: | :------------------- |
| `roomId`        | パス             | 文字列   |  必須  |  不可  | 空でない。           |
| `targetId`      | クエリパラメータ | 文字列   |  必須  |  不可  | 空でない。           |
| `schemaVersion` | クエリパラメータ | 文字列   |  必須  |  不可  | 2.2 を参照。         |
| `requestId`     | クエリパラメータ | 文字列   |  必須  |  不可  | 2.2 を参照。         |

#### 4.3.2 通知メッセージ

通知は、SSE の `data` に入れる JSON である。

| フィールド      | データ型 | 必須性 | NULL可 | 意味・取り得る値                                                                                                                |
| :-------------- | :------- | :----: | :----: | :------------------------------------------------------------------------------------------------------------------------------ |
| `schemaVersion` | 文字列   |  必須  |  不可  | 2.2 を参照。                                                                                                                    |
| `type`          | 文字列   |  必須  |  不可  | `CONTROL_UPDATED`（制御状態の更新。IF-006 の変更と、lease による保持者の変更）、`EVENTS_APPENDED`（イベントの追加）のいずれか。 |
| `controlSeq`    | 整数     |  必須  |  不可  | 通知の時点でサーバーが持つ最新の値。                                                                                            |
| `eventSeq`      | 整数     |  任意  |   可   | `EVENTS_APPENDED` のときの最新の順序番号。                                                                                      |

通知は更新の合図であり、最新の内容は IF-001 で取得する。

#### 4.3.3 エラー応答

接続の確立に失敗した場合は、通常の HTTP の応答（共通エラー形式）を返し、ストリームは開始しない。

ブラウザの EventSource は、接続に失敗したときのステータスと本文を読めず、区別のない `error` イベントだけを受け取る。そのため、クライアントは、IF-003 の接続エラーの原因を、直前の IF-001 の応答（同じエラーコードと共通エラー形式）で判別する。Control-First Sync では IF-001 が先に実行されるので、同じ原因のエラーは初回の接続では IF-001 で先に分かる。自動再接続が失敗した場合は `open` が発生せず、直前の IF-001 がない（例: サーバーの再起動で Room がなくなったとき）。EventSource は 200 以外の応答を受けると接続を閉じ、再接続しない（`readyState` が `CLOSED`）。そのため、`error` で接続が閉じた（`CLOSED`）ときは、クライアントが IF-001 を実行して原因を判別する。EventSource の代わりに fetch でストリームを読む実装にするかどうかは、DD で定める。

| エラーコード              | 発生条件                       | 応答形式            | 呼び出し側の対応         | 再試行可否 |
| :------------------------ | :----------------------------- | :------------------ | :----------------------- | :--------- |
| `INVALID_MESSAGE`         | クエリパラメータの欠落など。   | 400、共通エラー形式 | 接続の条件を修正する。   | 不可       |
| `ROOM_NOT_FOUND`          | `roomId` が存在しない。        | 404、共通エラー形式 | `roomId` を確認する。    | 不可       |
| `SCHEMA_VERSION_MISMATCH` | `schemaVersion` が一致しない。 | 400、共通エラー形式 | 状態を変えずに停止する。 | 不可       |

### 4.4 契約（IF-ID: IF-004 presence heartbeat）

- **概要**: 対象端末が、接続中であることをサーバーへ知らせる。サーバーは、この通知の TTL の切れで、オフラインを判定する。
- **呼び出し方式**: `POST /rooms/{roomId}/presence`。
- **冪等性**: あり。
- **事前条件 / 事後条件**: 事前条件は `roomId` が存在すること。IF-003 の接続がなくても、受け付けて期限を更新する（接続がなければ、BD D-04 の定義でオフラインと判定される）。事後条件は、対象端末の presence の期限が更新されること。期限の長さは DD で定める。オンラインかどうかは、`targetId` ごとに判定する（BD D-06）。

### 4.5 契約（IF-ID: IF-005 lease の取得・更新・解放）

- **概要**: 外部PCの操作者が、制御状態を変更する権限（lease）を取得し、更新し、解放する。更新が lease heartbeat に当たる。lease による保持者の変更は、制御状態の変更として扱い、`controlSeq` を発行する。
- **呼び出し方式**: `POST /rooms/{roomId}/lease`。`action` で、取得、更新、解放を区別する。
- **冪等性**: 更新と解放は冪等。取得は、すでに同じ操作者が保持していれば、更新として扱う。
- **事前条件 / 事後条件**:
  - 事後条件は、取得と更新の成功時に、サーバーが lease の期限を延ばしていること。期限の長さは DD で定める。
  - TTL の間に更新がなければ、サーバーが期限の時点で lease を解放し、`controlSeq` を発行して `CONTROL_UPDATED` を通知する。次のアクセスまで解放を遅らせない。期限を検出する方法は DD で定める。解放の後は、別の操作者が取得できる。

`controlSeq` を発行する条件は、保持者が実際に変わったときだけとする。

| 操作                                              | 保持者の変化  | `controlSeq` | `CONTROL_UPDATED` の通知 |
| :------------------------------------------------ | :------------ | :----------: | :----------------------: |
| `ACQUIRE`（新しく取得）                           | なし → 操作者 |   発行する   |           行う           |
| `ACQUIRE`（同じ操作者が保持中で、更新として扱う） | 変化なし      |  発行しない  |         行わない         |
| `RENEW`（lease heartbeat）                        | 変化なし      |  発行しない  |         行わない         |
| `RELEASE`                                         | 操作者 → なし |   発行する   |           行う           |
| TTL 切れによるサーバーの解放                      | 操作者 → なし |   発行する   |           行う           |

`RENEW` のたびに発行すると、heartbeat の周期で `controlSeq` が増え続け、対象端末の IF-002 が `STALE_CONTROL_SEQ` で拒否され続けるため、発行しない。

### 4.6 契約（IF-ID: IF-006 送信対象フィルタの変更）

- **概要**: lease を持つ外部PCの操作者が、送信対象フィルタを変更する。サーバーが `controlSeq` を発行する。現在の操作権限者の変更は、IF-005 で行う。
- **呼び出し方式**: `POST /rooms/{roomId}/control`。
- **冪等性**: 条件付き。クライアントが再試行するときは、同じ `X-Request-Id` を使う。同じ `requestId` の再送は、二重に適用されず、サーバーは最初の応答と同じ `controlSeq` を返す。サーバーが `requestId` ごとの最初の応答を保持する期間は、DD で定める。
- **事前条件 / 事後条件**: 事前条件は、呼び出した操作者が lease を保持していること（サーバーが判定する。BD D-01）と、`targetId` の対象端末がオンラインであること。事後条件は、変更が Room 全体に適用され、`controlSeq` が増加し、IF-003 で更新が通知されること。`targetId` の端末がオフラインの場合、変更は適用しない。
- **他の端末の扱い**: 同じ Room の他の端末がオフラインでも、拒否しない。それらの端末は、再接続時の IF-001（Pull）で最新の制御状態を受け取る（Control-First Sync）。端末ごとに送信を変えたい場合は、`sendFilter` の条件に端末の識別子を含める。形式は DD で定める。

## 5. 互換性・バージョン管理・変更管理

- **非推奨・廃止の手順**: v0.1 では定めない（#7）。
- **変更の通知先**: 親プロジェクトの担当者。
- **変更時の影響確認**: 本書を変更する場合は、BD、DD、DS、機能テスト要件への影響を確認し、要件定義書の FR-04 の記述との整合も確認する。
