# IF/API仕様書（外部インターフェース契約）
**対象端末・外部PC・サーバーのあいだの HTTP（Pull、Push、lease、presence）と SSE（更新通知）**

---

## 1. 概要とSSOT境界

### 1.1 対象インターフェースの目的

- **提供者 / 利用者**: 提供者はサーバー（v0.1 の参照実装は `relay`）。利用者は対象端末（ブラウザ）と外部PC（操作者）。
- **連携の目的**: 外部PCの操作に由来する制御状態を対象端末へ伝え、対象端末が制御状態に応じてイベントを送信するため。
- **対象範囲**: 制御状態の取得、イベントの送信、制御状態の変更、lease の取得・更新・解放、presence heartbeat、更新通知。
- **対象外**: 認証・認可（[#8](https://github.com/xzyozi/control-sync-ui/issues/8)）、タブ閉鎖中の要求の滞留（[#4](https://github.com/xzyozi/control-sync-ui/issues/4)）、複数操作者の競合ポリシー（[#2](https://github.com/xzyozi/control-sync-ui/issues/2)）。

### 1.2 単一責任範囲 (SSOT) と文書境界

- **本書の正本範囲**: `external_interface`。システム境界を越えるメッセージ、エラーコード、互換性の正本とする。
- **BDとの関係**: 境界の位置、ロックとオフラインの判定をサーバーが行う方針（D-01、D-02、D-04）は [基本設計書](./CSU-BD-001_基本設計書.md) を正本とする。本書はそれを接続契約へ具体化する。
- **DDとの関係**: 内部の DTO、制御フロー、状態遷移、TTL の具体値は DD（未作成）を正本とする。DD の作成後に、機能IDとの対応を追加する。
- **DSとの関係**: 保存後の形式は DS（未作成）を正本とする。本書は受信形式だけを定義する。
- **要件定義書との関係**: FR-04 の「Pull と Push は HTTP、更新通知は SSE」の記述は、本書を正本とする。要件定義書側は、後続の改訂で参照だけにする（#11）。
- **責務の対象外**: TTL と再試行の具体値、サーバー内部の順序付けの実装。
- **矛盾時の扱い**: 文書の更新日ではなく、該当する `ssot_scope` の正本を更新し、関連文書を追従させる。

## 2. インターフェース共通仕様

### 2.1 インターフェース一覧

| IF-ID  | インターフェース名           | 方向                     | 方式                          | 相手先                | 対応するDD機能ID | 状態 |
| :----- | :--------------------------- | :----------------------- | :---------------------------- | :-------------------- | :--------------- | :--- |
| IF-001 | 制御状態の取得（Pull）       | 対象端末 → サーバー      | HTTP（応答を返す要求）        | サーバー              | 未作成           | 計画 |
| IF-002 | イベントの送信（Push）       | 対象端末 → サーバー      | HTTP（応答を返す要求）        | サーバー              | 未作成           | 計画 |
| IF-003 | 更新通知                     | サーバー → 対象端末      | SSE（片方向のストリーム）     | 対象端末              | 未作成           | 計画 |
| IF-004 | presence heartbeat           | 対象端末 → サーバー      | HTTP（応答を返す要求）        | サーバー              | 未作成           | 計画 |
| IF-005 | lease の取得・更新・解放     | 外部PC → サーバー        | HTTP（応答を返す要求）        | サーバー              | 未作成           | 計画 |
| IF-006 | 制御状態の変更               | 外部PC → サーバー        | HTTP（応答を返す要求）        | サーバー              | 未作成           | 計画 |

IF-005 の更新が lease heartbeat に当たる。IF-004（presence heartbeat）とは、送り手も意味も異なる別のインターフェースである（BD D-02）。

### 2.2 共通ルール

- **プロトコル・トランスポート**: HTTP と SSE。通信の保護方式（TLS など）は、v0.1 の単体検証では対象外とし、#8 で定める。
- **データ形式・文字コード**: JSON、UTF-8。
- **時刻・タイムゾーン**: メッセージに時刻を含める場合は、UTC の ISO 8601 形式とする。lease と presence の期限の判定は、サーバーの時刻だけで行う。
- **識別子・相関ID**: Room を `roomId`、対象端末を `targetId`、外部PCの操作者を `operatorId` で識別する。リクエストごとに `requestId` を付け、応答とログで同じ値を使う。
- **共通メッセージ項目**: すべてのリクエストとメッセージに `schemaVersion`（必須、文字列）を付ける。
- **タイムアウト・再試行**: 具体値は DD で定める。再試行してよいかは、各 IF の冪等性と、エラー応答の再試行可否の列に従う。
- **利用制限**: v0.1 では定めない。

| 項目             | 内容                                                                                                                         |
| :--------------- | :--------------------------------------------------------------------------------------------------------------------------- |
| 認証方式         | v0.1 は認証を行わない。信頼できるネットワークでの単体検証だけを想定する（#8 で追加）。                                       |
| 認可（権限）単位 | v0.1 は Room 単位の分離と、lease による操作権限だけを扱う。lease の判定は認可ではなく、制御状態の排他制御である（BD D-01）。 |

| 権限不足時の応答 | lease を持たない操作者の制御状態の変更は、`LOCK_NOT_HELD` で拒否する（§4.6.3）。                                             |

## 4. インターフェース別契約

すべてのリクエストとメッセージに、2.2 の共通項目（`schemaVersion`、`requestId`）が付く。以降の表では、IF固有の項目だけを示す。形式の例は示さず、フィールドを表で定義する。

### 4.1 契約（IF-ID: IF-001 制御状態の取得）

- **概要**: 対象端末が、Room の最新の制御状態と `controlSeq` を取得する。接続・再接続時に、Push より先に必ず実行する（Control-First Sync）。
- **呼び出し方式**: Room の制御状態を取得する HTTP の取得要求。
- **冪等性**: あり。再送してよい。
- **事前条件 / 事後条件**: 事前条件は `roomId` が存在すること。事後条件は、応答の `controlSeq` が、サーバーが発行した最新の値であること。

#### 4.1.1 リクエスト

| フィールド | データ型 | 必須性 | NULL可 | バリデーション・制約          | 例・備考 |
| :--------- | :------- | :----: | :----: | :---------------------------- | :------- |
| `roomId`   | 文字列   | 必須   | 不可   | 空でない。                    |          |
| `targetId` | 文字列   | 必須   | 不可   | 空でない。Room 内で一意。     |          |

#### 4.1.2 レスポンス

| フィールド     | データ型 | 必須性 | NULL可 | 意味・取り得る値                                                           |
| :------------- | :------- | :----: | :----: | :------------------------------------------------------------------------- |
| `controlSeq`   | 整数     | 必須   | 不可   | サーバーが発行した最新の値。0 以上。                                       |
| `control`      | オブジェクト | 必須 | 不可 | 制御状態。`sendFilter`（送信対象フィルタ）と `holderId`（現在の操作権限者。なしの場合は NULL）を持つ。 |

#### 4.1.3 エラー応答

| エラーコード              | 発生条件                         | 応答形式       | 呼び出し側の対応                       | 再試行可否 |
| :------------------------ | :------------------------------- | :------------- | :------------------------------------- | :--------- |
| `SCHEMA_VERSION_MISMATCH` | `schemaVersion` が一致しない。   | クライアントエラー | 状態を変えずに停止し、呼び出し元へ通知する。 | 不可       |
| `ROOM_NOT_FOUND`          | `roomId` が存在しない。          | クライアントエラー | `roomId` を確認する。                  | 不可       |

### 4.2 契約（IF-ID: IF-002 イベントの送信）

- **概要**: 対象端末が、Reactive Outbox で選ばれたイベントをサーバーへ送る。
- **呼び出し方式**: Room にイベントを追加する HTTP の送信要求。
- **冪等性**: 条件付き。同じ `eventId` の再送は、二重に追加されない。
- **事前条件 / 事後条件**: 事前条件は、同じ接続での IF-001 が完了していること。事後条件は、受理されたイベントにサーバーが順序番号 `eventSeq` を付けていること。順序番号の範囲（Room 単位か全体か）は未決で、#11 で管理する。

#### 4.2.1 リクエスト

| フィールド     | データ型 | 必須性 | NULL可 | バリデーション・制約                                         | 例・備考                         |
| :------------- | :------- | :----: | :----: | :----------------------------------------------------------- | :------------------------------- |
| `roomId`       | 文字列   | 必須   | 不可   | 空でない。                                                   |                                  |
| `targetId`     | 文字列   | 必須   | 不可   | 空でない。                                                   |                                  |
| `controlSeq`   | 整数     | 必須   | 不可   | 送信を評価した時点の値。サーバーの最新値以下であること。     | Outbox が評価に使った値を付ける。 |
| `events`       | 配列     | 必須   | 不可   | 1件以上。各要素は `eventId`（文字列、一意）と `payload`（JSON）を持つ。 |                                  |

#### 4.2.2 レスポンス

| フィールド    | データ型 | 必須性 | NULL可 | 意味・取り得る値                                                       |
| :------------ | :------- | :----: | :----: | :--------------------------------------------------------------------- |
| `accepted`    | 配列     | 必須   | 不可   | 受理したイベントの `eventId` と、付与した `eventSeq` の組。            |

#### 4.2.3 エラー応答

| エラーコード              | 発生条件                                                       | 応答形式           | 呼び出し側の対応                                                                                                 | 再試行可否 |
| :------------------------ | :------------------------------------------------------------- | :----------------- | :--------------------------------------------------------------------------------------------------------------- | :--------- |
| `STALE_CONTROL_SEQ`       | 送信の `controlSeq` が、サーバーの最新値より古い。応答に最新の `controlSeq` を含める。 | クライアントエラー | IF-001 で制御状態を取得し直す。拒否されたイベントを再評価するのか破棄するのかは未決で、#11 で管理する。          | 条件付き   |
| `SCHEMA_VERSION_MISMATCH` | `schemaVersion` が一致しない。                                 | クライアントエラー | 状態を変えずに停止し、呼び出し元へ通知する。                                                                     | 不可       |
| `ROOM_NOT_FOUND`          | `roomId` が存在しない。                                        | クライアントエラー | `roomId` を確認する。                                                                                            | 不可       |
| `INVALID_MESSAGE`         | 必須項目の欠落、型の誤りなど、メッセージの形式が不正。         | クライアントエラー | 送信内容を修正する。                                                                                             | 不可       |

### 4.3 契約（IF-ID: IF-003 更新通知）

- **概要**: サーバーが、制御状態またはイベントが更新されたことを、接続中の対象端末へ通知する。サーバーから対象端末への片方向である。
- **呼び出し方式**: 対象端末が Room 単位で接続を確立し、サーバーがイベントを流す SSE のストリーム。
- **冪等性**: 該当しない（購読）。再接続後は、必ず IF-001 で最新の制御状態を取得する。
- **事前条件 / 事後条件**: 事前条件は `roomId` が存在すること。この接続の有無が、オフライン判定の条件の1つになる（BD D-04）。

#### 4.3.1 リクエスト（接続）

| フィールド | データ型 | 必須性 | NULL可 | バリデーション・制約 | 例・備考 |
| :--------- | :------- | :----: | :----: | :------------------- | :------- |
| `roomId`   | 文字列   | 必須   | 不可   | 空でない。           |          |
| `targetId` | 文字列   | 必須   | 不可   | 空でない。           |          |

#### 4.3.2 通知メッセージ

| フィールド     | データ型 | 必須性 | NULL可 | 意味・取り得る値                                                                                  |
| :------------- | :------- | :----: | :----: | :------------------------------------------------------------------------------------------------ |
| `type`         | 文字列   | 必須   | 不可   | `CONTROL_UPDATED`（制御状態の更新）、`EVENTS_APPENDED`（イベントの追加）のいずれか。             |
| `controlSeq`   | 整数     | 必須   | 不可   | 通知の時点でサーバーが持つ最新の値。                                                              |
| `eventSeq`     | 整数     | 任意   | 可     | `EVENTS_APPENDED` のときの最新の順序番号。                                                        |

通知は更新の合図であり、最新の内容は IF-001 で取得する。

#### 4.3.3 エラー応答

| エラーコード              | 発生条件                       | 応答形式           | 呼び出し側の対応                 | 再試行可否 |
| :------------------------ | :----------------------------- | :----------------- | :------------------------------- | :--------- |
| `ROOM_NOT_FOUND`          | `roomId` が存在しない。        | 接続時のエラー     | `roomId` を確認する。            | 不可       |
| `SCHEMA_VERSION_MISMATCH` | `schemaVersion` が一致しない。 | 接続時のエラー     | 状態を変えずに停止する。         | 不可       |

### 4.4 契約（IF-ID: IF-004 presence heartbeat）

- **概要**: 対象端末が、接続中であることをサーバーへ知らせる。サーバーは、この通知の TTL の切れで、オフラインを判定する。
- **呼び出し方式**: Room に対象端末の存在を通知する HTTP の送信要求。
- **冪等性**: あり。
- **事前条件 / 事後条件**: 事前条件は IF-003 の接続があること。事後条件は、対象端末の presence の期限が更新されること。期限の長さは DD で定める。

#### 4.4.1 リクエスト

| フィールド | データ型 | 必須性 | NULL可 | バリデーション・制約 | 例・備考 |
| :--------- | :------- | :----: | :----: | :------------------- | :------- |
| `roomId`   | 文字列   | 必須   | 不可   | 空でない。           |          |
| `targetId` | 文字列   | 必須   | 不可   | 空でない。           |          |

#### 4.4.2 レスポンス

応答の本文はない。受理されたことは、成功の応答だけで示す。

#### 4.4.3 エラー応答

| エラーコード              | 発生条件                       | 応答形式           | 呼び出し側の対応         | 再試行可否 |
| :------------------------ | :----------------------------- | :----------------- | :----------------------- | :--------- |
| `ROOM_NOT_FOUND`          | `roomId` が存在しない。        | クライアントエラー | `roomId` を確認する。    | 不可       |
| `SCHEMA_VERSION_MISMATCH` | `schemaVersion` が一致しない。 | クライアントエラー | 状態を変えずに停止する。 | 不可       |

### 4.5 契約（IF-ID: IF-005 lease の取得・更新・解放）

- **概要**: 外部PCの操作者が、制御状態を変更する権限（lease）を取得し、更新し、解放する。更新が lease heartbeat に当たる。
- **呼び出し方式**: Room の lease を操作する HTTP の送信要求。`action` で、取得、更新、解放を区別する。
- **冪等性**: 更新と解放は冪等。取得は、すでに同じ操作者が保持していれば、更新として扱う。
- **事前条件 / 事後条件**: 事後条件は、取得と更新の成功時に、サーバーが lease の期限を延ばしていること。期限の長さは DD で定める。TTL の間に更新がなければ、サーバーが lease を解放し、別の操作者が取得できる。

#### 4.5.1 リクエスト

| フィールド   | データ型 | 必須性 | NULL可 | バリデーション・制約                              | 例・備考 |
| :----------- | :------- | :----: | :----: | :------------------------------------------------ | :------- |
| `roomId`     | 文字列   | 必須   | 不可   | 空でない。                                        |          |
| `operatorId` | 文字列   | 必須   | 不可   | 空でない。                                        |          |
| `action`     | 文字列   | 必須   | 不可   | `ACQUIRE`、`RENEW`、`RELEASE` のいずれか。        |          |

#### 4.5.2 レスポンス

| フィールド   | データ型 | 必須性 | NULL可 | 意味・取り得る値                                   |
| :----------- | :------- | :----: | :----: | :------------------------------------------------- |
| `holderId`   | 文字列   | 必須   | 可     | 応答の時点の保持者。解放後は NULL。                |

#### 4.5.3 エラー応答

| エラーコード              | 発生条件                                                       | 応答形式           | 呼び出し側の対応                                           | 再試行可否 |
| :------------------------ | :------------------------------------------------------------- | :----------------- | :--------------------------------------------------------- | :--------- |
| `LOCK_HELD_BY_OTHER`      | `ACQUIRE` のとき、別の操作者が保持している。                   | クライアントエラー | 保持者の解放または TTL の切れを待つ。                      | 条件付き   |
| `LOCK_NOT_HELD`           | `RENEW` または `RELEASE` のとき、呼び出した操作者が保持していない（期限切れを含む）。 | クライアントエラー | `ACQUIRE` からやり直す。                                   | 不可       |
| `ROOM_NOT_FOUND`          | `roomId` が存在しない。                                        | クライアントエラー | `roomId` を確認する。                                      | 不可       |
| `SCHEMA_VERSION_MISMATCH` | `schemaVersion` が一致しない。                                 | クライアントエラー | 状態を変えずに停止する。                                   | 不可       |

### 4.6 契約（IF-ID: IF-006 制御状態の変更）

- **概要**: lease を持つ外部PCの操作者が、制御状態（送信対象フィルタ、現在の操作権限者）を変更する。サーバーが `controlSeq` を発行する。
- **呼び出し方式**: Room の制御状態を変更する HTTP の送信要求。
- **冪等性**: 条件付き。同じ `requestId` の再送は、二重に適用されない。
- **事前条件 / 事後条件**: 事前条件は、呼び出した操作者が lease を保持していること（サーバーが判定する。BD D-01）。事後条件は、`controlSeq` が増加し、IF-003 で更新が通知されること。

#### 4.6.1 リクエスト

| フィールド    | データ型     | 必須性 | NULL可 | バリデーション・制約                         | 例・備考 |
| :------------ | :----------- | :----: | :----: | :------------------------------------------- | :------- |
| `roomId`      | 文字列       | 必須   | 不可   | 空でない。                                   |          |
| `operatorId`  | 文字列       | 必須   | 不可   | 空でない。lease の保持者と一致すること。     |          |
| `targetId`    | 文字列       | 必須   | 不可   | 制御状態の変更を伝える対象端末。             |          |
| `sendFilter`  | オブジェクト | 必須   | 不可   | 送信対象フィルタ。形式は DD で定める。       |          |

#### 4.6.2 レスポンス

| フィールド   | データ型 | 必須性 | NULL可 | 意味・取り得る値                                       |
| :----------- | :------- | :----: | :----: | :----------------------------------------------------- |
| `controlSeq` | 整数     | 必須   | 不可   | この変更で、サーバーが発行した値。直前の値より大きい。 |

#### 4.6.3 エラー応答

| エラーコード              | 発生条件                                                                 | 応答形式           | 呼び出し側の対応                           | 再試行可否 |
| :------------------------ | :----------------------------------------------------------------------- | :----------------- | :----------------------------------------- | :--------- |
| `LOCK_NOT_HELD`           | 呼び出した操作者が lease を保持していない（期限切れを含む）。            | クライアントエラー | IF-005 で `ACQUIRE` からやり直す。         | 不可       |
| `TARGET_OFFLINE`          | `targetId` の対象端末が、BD D-04 の定義でオフライン。要求は滞留させない。 | クライアントエラー | 対象端末がオンラインになってから再実行する。 | 条件付き   |
| `ROOM_NOT_FOUND`          | `roomId` が存在しない。                                                  | クライアントエラー | `roomId` を確認する。                      | 不可       |
| `SCHEMA_VERSION_MISMATCH` | `schemaVersion` が一致しない。                                           | クライアントエラー | 状態を変えずに停止する。                   | 不可       |
| `INVALID_MESSAGE`         | 必須項目の欠落、型の誤りなど、メッセージの形式が不正。                   | クライアントエラー | 送信内容を修正する。                       | 不可       |

## 5. 互換性・バージョン管理・変更管理

- **バージョン方式**: すべてのメッセージの `schemaVersion`（文字列）で識別する。v0.1 の値は DD で定める。
- **後方互換性の範囲**: v0.1 は、`schemaVersion` が一致しないメッセージを受け付けない。互換とみなす変更の範囲は、スキーマ進化（アップキャスター）を扱う [#7](https://github.com/xzyozi/control-sync-ui/issues/7) で定める。
- **非推奨・廃止の手順**: v0.1 では定めない（#7）。
- **変更の通知先**: 親プロジェクトの担当者。
- **変更時の影響確認**: 本書を変更する場合は、BD、DD、DS、機能テスト要件への影響を確認し、要件定義書の FR-04 の記述との整合も確認する。
